## Context

The repository holds the `loop-workflow` contract and native OpenSpec integration for Claude, Codex and OpenCode, generated by OpenSpec 1.9.0. It has no package, code or CI. The legacy repository (pfa230/openspec-loop-legacy2) was a TypeScript ESM package with vitest, a pinned `@fission-ai/openspec` dependency and a CI workflow; it is a source of lessons, not of requirements. See proposal.md for motivation and the `loop-workflow` delta for the OpenSpec CLI requirement.

## Goals / Non-Goals

**Goals:**
- A clean checkout installs, builds and passes its declared check with nothing but Node and npm.
- The `loop` bin entry works end to end, so #3 adds commands to a packaging path that is already proven.
- The OpenSpec version decision is recorded in the contract before any code calls OpenSpec.

**Non-Goals:**
- Any controller behavior or command, including the OpenSpec version check. #3 implements the check when it adds `loop run` and `loop resume`.
- Publishing, the license and release documentation. These belong to #10.
- A linter or formatter. `tsc --strict` is the only static check until a concrete problem asks for more.
- Copying utilities or tests from the legacy repository. Each later build step copies a utility only for a concrete need and keeps its license notice.
- Anything from the session-handoff prototype (legacy commit 5e66447). The define-product-contract design already records it as evidence and drops the session bridge, so nothing is imported.

## Decisions

**TypeScript, ESM, `tsc` and `node:test`.** The controller mostly runs `git`, `openspec` and worker CLIs, so its tests will run real commands in temporary repositories rather than mock modules, and vitest's main advantage (module mocking, `expect` matchers) barely applies. Node's built-in runner leaves `typescript` and `@types/node` as the only dependencies, with nothing else to upgrade. vitest was rejected for its dependency tree and frequent major versions; plain JavaScript was rejected because the run state machine is where types catch mistakes cheaply. pfa chose this.

**Tests are compiled by `tsc` and run from the build output.** One `tsconfig.json` compiles `src/` and `test/` into `dist/`, and `node --test dist/test/` runs the compiled tests. The path is explicit because bare `node --test` on Node 24 also discovers the `.ts` sources and would run each test twice. This relies on no Node type-stripping behavior, so the check works the same on every Node version at or above the floor. Only the compiled `src/` ships in the package.

**Node 24 or later.** Node 22 reaches end of life on 2027-04-30; Node 24 is supported until 2028-04-30 ([endoflife.ai](https://endoflife.ai/article-nodejs-eol.html), [herodevs](https://herodevs.com/blog-posts/node-js-end-of-life-dates-you-should-be-aware-of)). Starting the first release on a line with six months left would force a floor bump soon after. `engines` declares `>=24` and CI runs Node 24.

**The loop uses the `openspec` on PATH, at 1.14.0 or later, with no upper bound.** The workflow has the user propose with native `/opsx:propose` and the loop validate and archive the same change, so both must use the same CLI. A pinned package dependency would put two versions on one `openspec/` tree: validation that passes by hand could fail at archival, archive could merge spec deltas differently, a proposal could use a feature the pinned version does not know, and the loop's agents would get different `openspec instructions` than the user's skills. Using the CLI on PATH removes all of these. The floor is the version current when this change was proposed, and the developer machine was upgraded to it. An upper bound was rejected: widening it on every OpenSpec release is recurring maintenance, and pfa prefers to fix an incompatibility after it appears. The package declares no OpenSpec dependency. pfa chose this.

**Native OpenSpec setup is regenerated with 1.14.0.** `openspec update` rewrites the generated skills and commands so the repository's own integration matches the floor. The configured schema stays `spec-driven`, and no custom schema is added.

**`loop` is declared now as a usage-only entry.** The contract names the command `loop`. The entry prints usage to stderr and exits with status 2, and the test runs the file the package's `bin.loop` names, so a wrong bin path fails the check. #3 replaces the usage-only body with the commands. A placeholder module without a bin was rejected because #3 would discard it, while it keeps this entry.

**`npm test` is the only declared check.** It runs the build and then the tests, so one command proves a checkout. CI runs `npm ci` and `npm test` on Node 24 for pushes to `main` and for pull requests. CI does not install OpenSpec, because nothing in this change calls it.

**`AGENTS.md` holds the agent instructions and `CLAUDE.md` imports it.** Codex and OpenCode read `AGENTS.md`; Claude Code reads `CLAUDE.md`, whose only content is `@AGENTS.md`. One copy cannot drift. The instructions point to `openspec/specs/loop-workflow/spec.md` as the source of truth, name `npm test` as the check, restate the minimal-by-design rule, and require edits in a worktree under `.worktrees/` on their own branch, because several sessions share the main checkout and a dirty main checkout blocks delivery.

**The package stays `private` until #10.** This prevents an accidental publish before the release step decides how the package is distributed.

## Risks / Trade-offs

- [A future OpenSpec release changes a command the loop relies on] → Most breakage surfaces as a failing `openspec` command, which the contract reports as an execution failure. A silent change in behavior, such as how archive merges deltas, would not be loud; pfa accepts fixing it after it appears.
- [Tests run from compiled output, so a test edit needs a build] → `npm test` always builds first.
- [`node:test` has weaker assertions and module mocking than vitest] → Accepted; tests drive real commands, and a runner can be swapped when a concrete test needs what `node:test` lacks.
- [Node 24 excludes users still on Node 22] → Accepted; Node 22 is in maintenance and ends in April 2027.
